# Contributing to Veklom

## The Foundational Governance Doctrine

As we evolve Veklom, we enforce strict criteria for what constitutes a foundational architecture change versus a feature, connector issue, or product improvement.

**No new foundational proof gate may be added unless failure of that gate would invalidate an already-sealed constitutional invariant.**

### What this means:
- **Constitutional Invariants:** Authority containment, Identity continuity, Constraint propagation, Consequence finality, Evidence continuity, and Epistemic discipline (see `CONFORMANCE.md`). 
- **Product vs. Protocol:** If a new system, agent connection, or dashboard visual fails, we ask: "Does this break the core invariants?" If no, it is a localized bug or feature enhancement. We do not reopen the question of whether Veklom fundamentally works.
- **Architectural Freezes:** The foundational layer is sealed. We build *on top of* and *in accordance with* the foundation, focusing entirely on enabling the next user milestone.

## Product Focus

Our immediate milestone is **Veklom Activation v1**. The focus for all contributions must be aligned towards enabling a user to:
1. Connect an automation
2. Grant bounded authority
3. Create one governed consequence
4. Observe one intentional denial
5. Inspect the evidence

...in under 60 minutes without developer assistance. Any contribution that does not directly stabilize, secure, or propel this flow is considered out of scope for the current operating cycle.
